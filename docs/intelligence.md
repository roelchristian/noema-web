## Intelligence and page summaries

Open **Settings → Intelligence** to save an OpenAI project API key. Keys are stored only in **macOS Keychain**, under a Noema service and a random account identifier per database. Other platforms fail closed until an OS credential-store adapter is implemented. SQLite stores only the random account identifier; database backups do not contain the credential. macOS may request Keychain access or require you to unlock your login keychain.

Noema provides no API or UI to reveal the saved key, including partial characters. The input clears on submission, and credentials are never placed in browser storage, process arguments, application logs, or provider error messages. The backend necessarily reads the credential into memory to authenticate HTTPS calls. Keychain protection depends on your macOS account and OS security: this is not protection against malware or an administrator controlling your computer. Local processes running as your user can access the local app; loopback access is not user authentication. Do not expose Noema through a reverse proxy or public tunnel.

The default lifetime is **30 days**, configurable from 1–365 days when saving or replacing a key. Expiry is checked before every AI use and a background sweep attempts removal every minute. When Noema is closed or Keychain is unavailable, physical removal waits until Noema can access Keychain again; expired credentials cannot be used through Noema. **Remove key** deletes the credential and aborts an active AI call. Replacement also invalidates active results. This lifetime is local to Noema: revoke a key in your OpenAI project to invalidate it at the provider. Keep a dedicated, restricted project key and configure project spending controls in OpenAI.

Use **Validate connection** to send a small test request without page content. This checks actual Responses API/model access and can incur a small charge. The existing default model remains `gpt-5-mini`, with reasoning effort defaulting to **low**. **Model** and **Reasoning effort** selectors offer a curated set of Responses API text models: GPT-6 Luna/Sol/Astra, GPT-6.1 Sol, GPT-5.6 Luna/Terra/Sol, and GPT-5 Mini. This catalog was checked against [official OpenAI model and reasoning documentation](https://developers.openai.com/api/docs/guides/latest-model) on October 16, 2026; it is not a live account-specific model list. Only compatible efforts appear, and the server rejects unsupported combinations. If changing models makes the current effort unsupported, the selector resets to low.

Choose **Save AI preferences** to persist model and effort across server restarts without reading, replacing, or extending the saved credential. Non-secret preferences are stored in SQLite; the API key remains in Keychain. Validation and summaries both use the saved selection; summary results display the model and effort used. Saving preferences aborts any active AI request and discards its result. Model availability depends on your OpenAI API project. Requests have a bounded output budget (2,048 tokens for validation; 8,192 for summaries, including reasoning) and the existing 45-second timeout. High effort may need more time or tokens than these limits permit; reduce effort or shorten the page if a response is incomplete.

On a page, choose **Knowledge → Summarize page**. Noema first saves pending edits, then sends only that saved page’s title, block text, and names of inline entity mentions. It excludes source bodies, entity properties, and other pages. Successful summaries are saved in SQLite and loaded when the Knowledge panel reopens, including after a server restart. Long summaries show three lines with a Show more / Show less toggle. Failed refreshes retain the previous saved summary. A locked vault, deleted page, changed revision, or removed/expired key prevents saving a new result. Closing the sidebar does not cancel an already transmitted request: a successful result is still saved, and provider charges may apply.

Choose **Knowledge → Scan for entities** to find potential knowledge entities in a note. Scanning saves pending edits and uses the configured model and reasoning effort. It sends the saved title and body text runs, current main types and subtype IDs, and this vault’s entity names, descriptions, and categories to OpenAI. Other notes and entity properties are excluded. Notes are limited to 40,000 body characters, and the full note/schema/catalog input to 80,000 characters.

Entity review retains streamed provisional suggestions, finalized batches of up to 25 suggestions, and saved continuation checkpoints. Provisional results cannot be accepted. Scan status, saved-batch review counts, and remaining text are reported separately; the review progress bar is not a complete-page scan percentage.

Choose **Contextual review** for a read-only page snapshot with exact highlighted block/cell evidence, a candidate queue, previous/next navigation and identity search. **View in page** opens the candidate in that snapshot; **Full block context** expands the local excerpt. Context comes from saved anchors and requires no extra model request. Alt+Left/Right moves between candidates and `/` opens identity search when focus is outside an input. Compact batch mode retains multiselection and atomic bulk decisions; narrow screens show stacked cards. Search and filters cover review status, entity type and identity status. Document order is the default; optional identity grouping and mode switches preserve draft edits.

The shared identity picker uses the existing name/alias ranking, with page usage breaking lexical ties. It displays saved descriptions, types and aliases and supports arrow keys and Enter. Ambiguous identities require an explicit choice. **Link existing entity** uses saved identity details; **Create and link** creates a new entity. Both preserve the occurrence’s original wording. The anchored evidence is always linked; additional occurrences are previewed and selected explicitly. Unselected occurrences remain excluded through save/reload using the existing occurrence-linking contract. Recorded scan exclusions can be reopened only for a pending anchored decision in the same revision-safe scan.

Suggested aliases are local proposals by default. Opting into **Save suggested aliases for future matching across this vault** changes the catalogue independently from document undo. Proposed dependent subtypes appear beside the entity decision and can be approved with it in the same transaction. Completion stays visible until dismissed, with **View changes** and **Return to page** actions. Rejection records a decision without creating an entity. Failed decisions preserve the review for retry. Scans, accepted/rejected decisions, selected anchors and partially reviewed batches persist with the note. Exact revision and scan-context checks reject stale reviews; **Scan again** replaces the previous scan. Failed scans retain the saved result. Scan attempts appear as **Entity scan** in the AI activity log.

The review API accepts optional suggestion edits with `saveAliases` (default false), `additionalOccurrences` (explicit block/cell offsets), and `approveSubtypeIds` (pending dependencies of that entity). All selected anchors, alias writes, schema decisions, entity creation and page updates share the existing transaction. Acceptance validates exact saved revision/context, eligibility, schema membership, occurrence boundaries, distinct anchors and segment limits before commit. Replaying a completed decision cannot create duplicate entities or links.

Page AI results use the shared `page_ai_enrichments` table, with one latest result per page and enrichment kind. Each result stores a JSON payload, source page revision, model, reasoning effort, and timestamp. Summary and generated-title results use this storage; future enrichment handlers can use the same service. Saving an enrichment does not change the editor revision. Later page edits retain results and the summary shows when its source revision is older. Vault scoping and locks protect retrieval; Trash retains results for restoration, and permanent page deletion cascades to them. Clearing the AI activity log does not erase enrichments.

Untitled pages automatically receive a title after a successful save and **three seconds without edits**, once their body contains at least **20 characters**. Opening an existing untitled page resumes this workflow after a reload or vault switch. The title utility sends only that page's text and inline entity names, and uses reasoning effort fixed to **none**, independently of the reasoning preference. It uses the selected model when the existing model catalog supports `none`, otherwise GPT-6 Luna, with a 256-token output budget. The prompt favors compact subject labels of 2–6 words, preferably within 50 characters, rather than summaries of every detail. Titles have a hard limit of 120 characters and are saved through autosave. Edits, manual titles, deletion, and vault changes discard outstanding results. Empty pages and pages with a title are excluded. Temporary provider, rate-limit, and network failures retry up to twice, after 15 seconds and then 60 seconds; edits or a vault switch invalidate pending retries. Missing credentials and permanent failures stay quiet; another saved edit or reopening the page can try again. Automatic title generation can incur API charges and appears as **Page title** in the activity log.

Security controls include private IPv4 LAN access enabled by default with a persisted localhost-only toggle in Settings → Security; peer-address checks and an explicit Host allowlist; same-origin checks; a custom request header and JSON requirement on AI endpoints; no cross-origin access; no response caching; a fixed HTTPS OpenAI endpoint with redirects disabled; no model tools; 40,000 input characters; bounded provider responses and output tokens; a 45-second timeout; one active AI call and five attempts per minute per server process; and sanitized errors. Rate limits are local safeguards, not a billing cap. Page content is treated as untrusted input, and output is never executed.

The summary prompt keeps Noema’s fixed instructions separate from note text. Titles, body text, and mentioned entity names are serialized into a JSON `untrusted_note` string inside a single lower-priority user message. No note text is interpolated into trusted instructions or used to construct roles, tools, model settings, or conversation history. Noema explicitly directs the model to summarize embedded instructions as document content rather than obeying them, including fake roles, delimiter escapes, encoded commands, and authorization claims. Requests explicitly set `tools: []` and `tool_choice: "none"`; results remain inert plain text.

This follows [OpenAI’s guidance on separating untrusted input from trusted instructions](https://developers.openai.com/api/docs/guides/agent-builder-safety). It reduces prompt-injection risk but cannot guarantee model-level immunity. Regression tests use malicious note fixtures to verify request isolation, not to claim live-model robustness; no live attack evaluation was run with a billable API key.

Requests use the [OpenAI Responses API](https://developers.openai.com/api/docs/guides/text) with `store: false`. This does not guarantee zero provider retention; see [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data) for applicable processing and retention policies.

**Settings → Intelligence → AI debug mode** enables compact diagnostics for new requests. It is off by default and applies across vaults. Compact traces retain request configuration and input sizes, bounded output excerpts, provider metadata and usage, validation diagnostics, and an aggregated stream timeline. They omit note bodies, embedding vectors, raw SSE bodies, and individual text deltas. Authorization headers are excluded and recognizable API keys are redacted. Generation requests use streaming while debug capture is enabled. Token accounting remains independent of debug capture.

For a difficult investigation, start a deliberate **Full trace** session in debug settings. The session expires automatically and subsequent requests return to compact capture; stopping the session also restores compact mode. Full captures can contain private note text and generated output, but never embedding vectors. Trace limits do not change provider output limits or interrupt generation.

New compact successes retain at most 16 KiB, compact failures at most 64 KiB, and full traces at most 2 MiB per request. Completed debug traces in every mode expire after 30 days, measured from request completion. Traces share a 50 MiB payload budget, which can remove older completed traces sooner while protecting active requests. Activity and token accounting are retained independently for one calendar year without a record-count ceiling. These are logical retained-payload limits, not SQLite file-size limits. SQLite can reuse freed pages; this change does not run VACUUM or compact the live database file.

In **AI activity log**, choose **Open payload** for the diagnostic overview and expandable excerpts. Running requests poll by revision; polling stops on completion. Full and historical stream events load only when expanded and are paginated. JSON download includes the diagnostic summary and available event pages; CSV contains activity metadata only. Historical traces follow the same 30-day and byte limits. Deleting debug traces preserves activity and token usage for the chart.

Turning debug mode off stops capture for subsequent requests without deleting previous traces. Vault locks hide payloads; clearing activity and deleting a vault remove associated traces. Debug settings and traces are excluded from vault exports.

### Speak and saved audio

Enable **OpenAI text to speech** in **Settings → Intelligence** and save AI preferences. In the editor, open a selected block’s menu and choose **Speak**, below **AI actions**. Choose **TTS voice** and save AI preferences to apply it across vaults. Speech uses `gpt-realtime-2.1-mini` with the selected voice (Marin by default), independently of the writing model. Changing voices generates and saves separate audio; switching back reuses that voice’s recording when the text is unchanged. Changing voice also stops playback and any speech generation in progress. Only the selected readable body text is sent to OpenAI: Noema block IDs, semantic tags, group metadata, provenance, link destinations, references, citation chips, reference markers, and Markdown footnotes are excluded. Readable entity names remain part of the prose; their IDs and metadata stay local. Page IDs are retained locally for the activity log. The player offers **Download audio** to save the complete selected text as a WAV file. Long selections are generated in parts and joined into one recording before playback and download.

Generated speech is saved in `data/assets/<vault-id>/speech/`, beside the vault’s other assets. Replaying unchanged text reuses its saved audio, including after a restart, without an OpenAI request or another API charge. Changes to the text, speech model, voice, narration instructions, or audio format create a new cache entry. Formatting alone does not invalidate it. Saved audio stays local, follows vault access locks, appears under **Storage → Attachments**, and is included in vault backups. Deleting the vault removes its saved speech. Removing the API key does not prevent replaying cached speech while the global speech option remains enabled.

Only requests that generate audio create AI activity records; local cache hits and downloads do not. Selected text and audio are omitted from debug traces, including full traces. Token usage is recorded when supplied by OpenAI; speech cost remains unknown because the generic text-model pricing table does not distinguish audio rates.

### AI activity notifications

The toolbar bell uses a small theme-colored dot for unread enrichment updates and work in progress across unlocked vaults, with no numeric badge. Manual summaries and entity scans, automatic titles, and background producers using the shared enrichment service all feed the same local queue. A title notification appears only after the generated title is actually applied to the note. Summaries and scans notify after their result is saved. Failed or interrupted provider attempts appear too; routine indexing successes, search queries, and connection tests remain in the full activity log.

Open a notification to visit its note and mark it read, dismiss its unread dot, or choose **Mark all read**. Read state persists in SQLite across reloads and restarts. Opening the menu alone does not mark anything read. **Recent** includes read updates, and **View full activity log** opens the detailed history. The queue refreshes every five seconds while the app is visible and after local enrichment results or saves. Notifications contain references and status, without copies of note text, generated output, or titles. Locked vaults are hidden; permanent note deletion removes its notifications. The latest 1,000 notifications are retained. Unsaved and failed save indicators remain visible separately, with click-to-retry on failure.

### AI activity log

Settings → AI activity log shows page summaries, entity scans, automatic titles, note embedding attempts, semantic-search embeddings, and connection tests, backed by the local SQLite `ai_activity` table. Each entry records status, start/finish time, duration, HTTP outcome, model and reasoning effort, the page/vault ID and revision (when available), and prompt size in UTF-8 bytes. The size includes instructions and input text, including the note wrapper; it is not a token count. Prompt text, generated text, credentials, and provider error bodies are never stored in the log. Embedding entries use the fixed embedding model and input size, with no reasoning setting. Note embeddings link to the source note and revision; search embeddings show the vault without retaining the query. Each actual indexing attempt, including retries, has a separate record. Queued jobs remain in embedding settings; skipped local jobs that never request an embedding do not create activity. Results discarded after a note edit or cancellation are marked skipped, and shutdown marks active attempts interrupted.

The backend retains one calendar year of activity and token usage with no record-count limit, preserving running requests until they finish. Debug payloads expire separately after 30 days; their deletion does not remove token history. The token usage view includes a **1 year** period and loads every retained page of activity. Requests left running after a server restart become interrupted. Settings loads 50 entries at a time, offers older activity and manual refresh, and links to available source pages. Page titles are resolved from the current page rather than copied into the log; deleted pages retain only their reference. Activity in locked vaults stays hidden until the vault is unlocked.

`GET /api/intelligence/activity` returns `{items, nextCursor}`; pass `?before=<nextCursor>` for the next page. It uses the same local-origin and `X-Noema-Request: 1` protections as other Intelligence endpoints. Authorized action attempts include local failures such as stale revisions, missing credentials, and rate limits; requests rejected by origin/client checks are not logged.

## Entity discovery limits

AI discovery retains the existing limit of 40,000 text characters and 80,000 serialized input characters per explicit scan. Longer reviews continue from saved 25-suggestion checkpoints; per-block AI result caching remains future work. Existing AI activity logging records request usage and timing; dedicated recognition-quality benchmarks are not yet included.

## Activity token accounting

AI activity records and CSV exports include provider-reported cached-input and cache-write tokens independently of optional debug traces. Missing values stay unknown; reported zeros remain zero. Existing debug responses backfill available counts on startup. Local query-cache hits do not create provider-request records.

See [page classification drift policy](page-classification-drift-policy.md) for enrichment scheduling, field ownership, and classification freshness.

## Server generation request contract

`Intelligence.generate` accepts one `GenerationRequest` from `server/modules/generation-request.ts`. The discriminated `kind` names the intent; `onRequest`, `background`, and `signal` are common named fields. Validation carries no note input. Streaming callbacks belong only to entity scans, source math, and source pages; preliminary preview callbacks belong only to source pages.

```ts
await intelligence.generate({kind:'review',input:JSON.stringify({untrusted_texts:texts}),onRequest:observe});
await intelligence.generate({kind:'sourceMath',input,background:true,signal,onRequest:observe});
await intelligence.generate({kind:'entityScan',input,signal,onDelta,onRequest:observe});
```

The exhaustive `generationPolicy` switch selects the existing prompt, model/effort, token and output limits, timeout, stream channels, and admission policy. Prompt construction remains lazy so it runs after admission inside the existing provider error boundary. Titles/utility, entity scans, and page enrichment are independent of the exclusive active-generation slot. All other kinds claim that slot, including background source math, metadata/authors, and editorial work. `background` bypasses only the manual per-minute budget; it does not bypass the active slot. Source math/page and editorial keep the 180-second limit; other kinds keep 45 seconds, all capped by credential expiry.

Credential access, replacement/expiry checks, redaction, request tracking, transport, and response reading remain in `Intelligence`. Feature parsing and revision/ownership checks remain in their existing modules. The narrow `generateTitle`, `generatePageUtility`, `generatePageEnrichment`, `enrichSource`, `extractSourceAuthors`, and `reeditSource` facades retain their feature contracts and parsers; they delegate to the named request API. In particular, page enrichment still validates requested fields before credential access/admission. These are feature seams, not a retained positional `generate` overload. The legacy HTTP title/PageUtility compatibility behavior is unchanged.

The synthetic checked matrix in `test/helpers/generation-contract.ts` covers every request kind. `test/fixtures/generation-contract.json` freezes complete prompt/input/schema digests, observer byte counts, and readable provider policy fields captured from main `2bc0b3a6cf8e6e4c94a6f8980fbcc19579cd75d0` before the migration. Four compact cases in `intelligence.test.mjs` cover payload parity; admission in both directions and manual/background accounting; timeout/output boundaries, abort, expiry, replacement and errors; and final/preview streaming, usage and redaction. Existing feature/integration cases retain parser, stale-revision, lock and ownership coverage. No live provider calls or user data are required.

### Debug capture benchmark

Run `node --import tsx scripts/benchmark-ai-debug.mjs` to compare compact and full capture using temporary databases and the same synthetic 500-delta provider stream. It reports retained bytes, debug writes, event insertions, summary response sizes, WAL growth, and checkpointed database growth. It never reads the user's database or calls OpenAI. One local run retained 4,931 bytes in compact mode versus 119,389 in full mode, inserted zero versus 501 stream event rows, and produced 86,552 versus 4,132,392 WAL bytes. These results describe this fixture, rather than a forecast for real workloads.

### Cleaning up existing debug payloads

Run `node --import tsx scripts/cleanup-ai-debug.mjs` from the repository root to remove completed debug traces from `data/noema.sqlite`; an optional database path or `DB_PATH` selects another database. Cleanup recovers provider-reported usage from old responses first, retains activity/token records within the one-year window, and leaves active requests and their traces alone. It includes locked-vault traces but does not alter vault contents. The command reports before/after counts and token totals. `Clear activity` also removes usage history; use the cleanup command when preserving chart history matters.

Add `--vacuum` to reclaim freed SQLite file space. This uses SQLite's transactional VACUUM and skips it when an AI request is active; other writes may briefly wait while compaction runs. Without VACUUM, freed pages remain available for reuse.
