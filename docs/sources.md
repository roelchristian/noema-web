## Attach and read sources

- In the top toolbar’s **Sources** menu, attach an existing Source or create a new one. Remove a page source with **×**; the Source entity remains in the vault.
- Choose **Source** when creating an entity to represent a reference. Choose one original **TXT, MD, or PDF** file (up to 50 MB), a public URL, or pasted text before creating it. Sources keep the same properties, relationships, subtypes, aliases, and inline `@` mentions as other knowledge entities.
- In **Sources → New source**, choose **Paste text**, paste into **Source text**, edit the suggested **Pasted text** name if needed, then choose **Create source**. Pasted text is validated against the existing 16 MB UTF-8 extracted-text limit and uploaded as a TXT original; no source URL is invented. Unicode and blank-line paragraph boundaries are retained, with the original bytes stored for provenance/download and the existing local normalization applied to the reading copy. Failed validation or creation keeps the draft. A retry reuses an already staged original. Existing Intelligence enrichment and optional semantic-indexing settings/disclosures apply exactly as for uploaded TXT sources; pasting or editing the form itself makes no AI request.
- Open **Sources** between Inbox and Knowledge entities in the sidebar for the source library. Sources are excluded from Knowledge entities browsing, search, and counts, while remaining Source entities in the backend. Clicking a Source opens a read-only document workspace with mathematical notation, attachment selection, and stable passage references in the document margin. The **Source inspector** toolbar button shows metadata, connections, and processing details alongside the document. Its Overview follows the selected attachment with a collapsible AI summary, populated metadata, and direct retry actions. Connections groups page mentions and relationship editing; Details contains metadata editing, files, and technical exports. The inspector remembers its visibility and selected tab while browsing sources, and Escape closes it and returns focus to its toolbar button. Select a passage by its reference to **Copy citation**, **Add to page**, or **Annotate**. Passages and annotations are saved with citations in a new or existing note; imported source text remains read-only. Source workspaces support back/forward navigation and direct links.
- Select text in the Source reader to show a contextual menu after selection finishes. **Highlight passage** offers yellow, green, blue, pink, and purple. **Add reading note** saves a source-linked mini-note as a page with a 200-word body limit, enforced on creation and later edits. Saving dismisses the popover and adds a clickable note marker at the start of the annotated line; markers reload when the source is reopened. Highlights and reading-note passage anchors live in separate `highlights` and `page_reading_notes` tables; imported source text stays unchanged. Highlights are rendered only on the matching source text version. Both layers are included in vault backups.
- A floating reading pill shows the current physical page and previous/next controls when the source records page boundaries; other sources navigate by section or passage. Click an existing highlight (or focus it and press Enter) to change its color or add a reading note. Color changes update the same stored highlight.
- Each original is stored with a UUID filename at `assets/<vault-id>/sources/<uuid>.<extension>` beside the database. The original name and extracted text are stored in `source_files`. Text sources must be UTF-8. HTML uploads and extraction are disabled. Existing HTML originals remain available for download or replacement.
- Extraction runs in a local background queue. The source panel shows waiting, extraction progress, ready, or failure states. You can read extracted text, download the original, retry failed extraction, or attach replacement files. The last attached file cannot be removed. The original remains available even when extraction fails. Interrupted jobs resume on restart; locked vaults do not start new extraction jobs. Unattached uploads expire after 24 hours during startup/hourly cleanup.
- On **macOS**, PDFKit reads embedded PDF text and Apple Vision OCR reads pages with little or no embedded text, including mixed scanned/digital PDFs. Nothing is sent to an AI provider. The first PDF extraction compiles `scripts/extract-source.swift` using the macOS Command Line Tools (`xcode-select --install` if needed), then caches the executable beside the assets. PDFs support up to 1,000 pages, 16 MB of extracted text, and a 10-minute extraction timeout. Password-protected, damaged, empty, or unreadable PDFs show a retryable error. Other operating systems currently support TXT and MD extraction; PDF originals can still be saved and downloaded but PDF extraction reports the macOS requirement.
- Existing Source entities remain intact and show an attachment prompt if they have no original. New sources require attachments through the API as well as the UI. To preserve file ownership, file-backed sources cannot change entity type. AI entity scans can link existing sources; create new sources manually with their original files first.
- Vault backups include attached originals and their extracted text/status, remapping file UUIDs when imported. Older backups without file attachments remain importable.

## Archive or delete an unused source

In **Sources**, choose **Manage** on a source to check its linked pages and archive it. Switch **Active sources** to **Archived sources** to restore an archived source or permanently delete it. Archiving keeps original files, highlights, metadata, and connections; archive status is included in vault backups.

For now, sources with linked pages cannot be archived or deleted. This check includes pages in Trash, attached page sources, citations, reading notes, generated pages, and inline mentions. The server rechecks links inside the mutation transaction, so a stale dialog cannot bypass the restriction. Source processing and pending page drafts also block removal; finish processing and accept or discard the draft first.

Permanent deletion requires archiving first and typing the exact current source name. It removes the source, its highlights and metadata, and entity connections. Original file records are detached in the same transaction and retained for the existing orphan-file cleanup, which removes them after 24 hours at startup or on an hourly cleanup run. Deletion has no restore action; export a vault backup beforehand if needed.

Lifecycle API (with the usual vault access checks and mutation headers): `GET /api/entities/:id/lifecycle` returns eligibility and a linked-page count; `POST` to the same endpoint accepts `{action: "archive"}`, `{action: "restore"}`, or `{action: "delete", confirmation: "<exact source name>"}`. Linked or busy sources return HTTP 409 on removal.

## Processing and page generation

Long-source progress distinguishes extraction, math preparation, AI planning, streaming, and reference checks. Extraction estimates use observed progress; math preparation reports completed batches and estimates remaining uncached work from measured batch durations. Page generation shows elapsed time and, when at least three similar completed requests exist for the same model and reasoning effort, a historical duration estimate. Estimates are approximate, never fabricated percentages, and overdue estimates become a still-working message. Source extraction/enrichment continues after leaving its panel; closing page generation cancels that request while retaining completed math checkpoints.

Math-heavy sources receive an additional span-preparation pass during enrichment (and before page generation for older sources). A local detector skips ordinary prose. AI returns compact replacements for mathematical spans using `$...$` or `$$...$$`, while surrounding prose stays intact. The application verifies exact span locations and KaTeX syntax, preserves line counts and physical page mappings, and records ambiguous OCR in `processing.math.uncertain` using one-based line numbers. This is notation preparation, not a guarantee that damaged OCR can be reconstructed.

The cleaned text is saved separately from the original extraction and becomes the input for processed JSON, passage indexing, page generation, and new citation excerpts/verification. The citation viewer selects the version matching each citation's hash, so older references still open their original extraction. Cleaned text is included in vault backups. Math preparation shares the page-generation limit of 160 KB of extracted text; larger sources must be split. Small batches are checkpointed and the completed cleaned source is reused until the extraction changes; unchanged prose is not echoed in model output.

## Structured source documents

**Download processed JSON** is available under **Details → Technical export** in the source inspector after extraction (and alongside the original in the general entity panel). The versioned `*.processed.json` document has two independent structures: `physical.pages` records physical page ranges, while `semantic.children` nests chapters, sections, subsections, and labelled theorem, lemma, proposition, corollary, definition, proof, example, and remark blocks. Content leaves contain paragraphs, lists, equations, code, tables, or quotes. A semantic block can span multiple physical pages; a page is never its semantic parent. Each node includes extracted-line and UTF-16 offset ranges plus physical page positions when available. Line/page numbers are one-based; offsets are zero-based with an exclusive end. Missing page maps remain unknown.

The document is assembled locally from stored text and markers, including for older sources. AI enrichment requests only compact marker kinds and line ranges in the same response as source metadata, without echoing source text. Long inputs retain bounded excerpts, so local detection covers the remaining text and the JSON does not imply exhaustive AI classification. Statement/proof extents inferred by local rules are marked `inferred`; AI-provided end lines are marked `explicit`. OCR content is preserved rather than silently repaired, and exporting never changes citation coordinates or starts an AI request. Source-to-page generation consumes the nested document itself: each paragraph or block body is included once, with its kind and original line range. Physical pages remain separate. Leaves spanning more than 30 source lines are split locally to fit the citation limit. No duplicate raw-text copy or truncated outline is sent.

Structured source documents are persisted in the derived `source_documents` table. Downloads and page generation share this representation; a builder version and input fingerprint refresh it when source text, markers, page positions, or metadata change. Originals and citation coordinates are not rewritten. The cache can be rebuilt after backup restore.

To migrate existing ready sources in one unlocked vault without AI requests:

```sh
node --import tsx scripts/migrate-source-documents.ts --vault <vault-id> --db data/noema.sqlite
```

The migration is idempotent and reports migrated, current, and skipped sources. It requires an explicit vault ID and leaves unrelated vaults alone.

## Editorial reprocessing (beta)

A processed attachment can be re-edited through **Reprocess with AI** in the source reader's beta workflow. Start a revision with optional instructions about the particular document. The request uses the configured AI model with **medium** reasoning for this workflow; it does not change the normal Intelligence preferences. No new editorial pass starts merely by opening a source or switching views.

Wait for the initial source enrichment to finish before starting an editorial pass.

The original processed Markdown and structured JSON remain canonical for citations, highlights, search, and source-to-page generation. Reprocessing stores a separate snapshot and editorial proposals. Cleanup can address OCR mistakes, accidental line breaks, mathematical notation, footnotes, foreign-language citations, document metadata, and printed page apparatus. Original wording, physical page mappings, and semantic node identities remain available for comparison. Foreign-language quotations should remain in their original language; editorial cleanup is not translation or invention of missing text.

Switch between the original processed view and a reprocessed revision. Review the original and proposed wording, accept or reject suggestions, or supply a correction before accepting. Every proposed change starts pending, including high-confidence edits; only accepted changes enter the reprocessed reading view. Page apparatus can be removed from the reading presentation while its original content and location remain in the revision's provenance. Use the original-view links for canonical passage actions; rewritten offsets must not become citation anchors.

Each revision includes a processing report with the model, reasoning effort, prompt version, elapsed time, coverage, diagnostics, provider-reported token usage, and failures. Malformed, ambiguous, overlapping, or page-boundary-changing individual suggestions are excluded from the review queue and recorded with their rejection reason in processing diagnostics; valid suggestions continue through the remaining excerpts. A malformed response envelope or provider failure still fails the run and preserves completed excerpts. Missing usage is unknown rather than zero. Export the original and reprocessed JSON together with their provenance for meaningful comparison and iterative prompt refinement. Revisions, reports, and review decisions are included in vault backups; restoring a backup does not restart paid processing. A stale revision remains a record of the snapshot it processed and must not silently overwrite a newer canonical source.

## Source file API

Source file API: `POST /api/source-files?name=<filename>[&entity=<source-id>]` accepts the original binary body with `X-Noema-Request: 1` and `X-Vault-Id`. For new sources, upload files first and pass their IDs as `attachmentIds` to `POST /api/entities` with `type: "source"`. Existing-source uploads use the `entity` query parameter. `GET /api/source-files/:id` returns extraction state and text; `GET /api/source-files/:id/download?vault=<vault-id>` downloads the original safely as an attachment; `POST /api/source-files/:id/retry` retries failed extraction; `DELETE /api/source-files/:id` removes a file while enforcing the last-file rule. All actions enforce vault scope and locks.

### Beta reprocessing API

All endpoints use the existing vault access checks. Mutations require `X-Noema-Request: 1` and a JSON content type.

- `GET /api/source-files/:id/reprocessing` lists saved passes and their coverage/status summaries.
- `POST /api/source-files/:id/reprocessing` with `{instructions?: string}` starts a separate pass and returns HTTP 202 with the revision. Guidance is limited to 4,000 characters; the beta bounds source size to 512,000 characters. Large documents are reviewed in bounded excerpts with surrounding context, not sampled silently; this beta allows at most 128 excerpts and 5,000 semantic nodes and keeps each excerpt within a physical page when page boundaries are available. Accepted custom edits are capped at 1,024,000 characters in the resulting reading version.
- `GET /api/source-files/:id/reprocessing/:revisionId` returns both version snapshots, canonical fingerprint, exact-span patches, semantic-node links, and the processing report.
- `POST /api/source-files/:id/reprocessing/:revisionId/review` accepts `{updatedAt, decisions: [{patchId, decision, replacement?}]}`. Decisions are `accepted`, `rejected`, or `pending`. `updatedAt` must match the current revision to prevent overwriting another review. A custom replacement is optional; page markers cannot be rewritten.

Runs continue in the background while the app is open. Closing the server or locking its vault interrupts active work; completed excerpt suggestions and diagnostics remain available. Interrupted jobs require an explicit new pass, so reopening the app does not repeat paid requests. Failed or incomplete passes report their actual coverage rather than claiming full-document completion. The local report checks footnote references/definitions, supported math syntax, and physical page markers, but cannot certify transcription accuracy or mathematical meaning.
